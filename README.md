# DrillMap

DrillMap is a self-serve LSAT study-planning app. It turns a student's 7Sage
analytics into a targeted Monday–Sunday drilling plan. Each new weekly schedule
uses approved analytics and reported progress; a saved week stays fixed.

The schedule is generated by deterministic rules, not an LLM. Claude Vision is
used only to extract structured data from a student-uploaded 7Sage screenshot;
the student reviews that extraction before it becomes the current analytics
snapshot.

## Current state

The app stores its records in Postgres. See [Postgres setup and tests](docs/postgres-foundation.md) for the local
startup command, migrations, and database tests.

The core student workflow is implemented:

- Google sign-in, with separate student and admin roles. Password sign-in waits for a DrillMap domain (#222).
- Student signup, onboarding, profile editing, and a weekly dashboard
- A deterministic scheduling engine with coverage for its rules
- Append-only approved Analytics snapshots in Postgres
- One immutable adaptive weekly schedule per student/week, with activity check-ins that shape a future unsaved schedule
- A read-only admin view of each student's saved schedule and check-in state
- Public landing, legal, login, and signup pages

Billing is intentionally deferred. The tracked next feature is
[Issue #13: Stripe subscriptions, a seven-day trial, and the 7Sage referral
discount](https://github.com/Jahazel/lsat-scheduler/issues/13).

## Key product decisions

- Analytics arrive through 7Sage screenshot upload; the app does not scrape
  7Sage or share student credentials.
- The engine outputs a study-plan shopping list—question type, count,
  difficulty, and PT-130 side—not licensed LSAT question numbers.
- Students set capacity for each day and choose a preferred practice-test day.
  A practice-test review day follows each practice test, and the rest day moves
  off Wednesday when one of them takes it; the specification lists every case.
  Near-test weeks can contain two LawHub practice tests.
- Every drilling day has a daily minimum. The practice test, its review,
  a full section, or the daily minimum can exceed daily capacity; the day card
  shows the overage. Other drilling work stays within its fill limit.
- The `adaptive-weekly-schedule-v2` policy saves reason sentences when it
  creates a schedule. Past weeks keep their planned work, capacities, and wording.
- AI does not decide the plan or change its rules.

## Stack

- Next.js, TypeScript, React, and Tailwind CSS
- Postgres with Drizzle ORM
- Auth.js / NextAuth with credential and Google sign-in
- Anthropic API for screenshot analytics extraction
- Vercel for deployment

Uploaded analytics images are used in memory for extraction and are not stored
by the application.

## Local setup

Install Node.js 20.9 or later with npm. Local database setup needs either
Docker with Compose or an existing Postgres 17 installation.

The Stage 1 pause on local data writes ended on October 8, 2026 after the
separation, real-site, and local validation checks passed under the owner's
evidence exception for unavailable old credentials. See
[issue #86](https://github.com/Jahazel/lsat-scheduler/issues/86) and the
validation evidence (issue #86). The no-promotion rule
remains in force. This does not approve launch.

The steps below describe setup for a new copy of the repository. Local work uses
Postgres on your Mac with test data only. A loopback address accepts connections
from this computer only. Never keep real-site credentials in local files. A
credential is a secret that gives access, such as a password or an API key.

1. Install the app dependencies from the repository folder:

   ```bash
   npm install
   ```

2. Start local Postgres and apply the migrations. Follow
   [Postgres setup and tests](docs/postgres-foundation.md). It covers the Docker
   container and an existing Postgres 17 install.

   Migrations create the database tables. The migration command reads
   `DATABASE_URL` from the terminal environment, so use the explicit loopback
   value shown in that guide. It does not load `.env.local`.

3. Copy `.env.example` to `.env.local` for this new local setup:

   ```bash
   cp .env.example .env.local
   ```

   Keep `DATABASE_URL` at a loopback address. This connection string tells the
   app where to find the local database. Generate a new local Auth.js secret
   with the command in `.env.example`. Auth.js uses this secret to protect
   sign-in sessions. Put it in `AUTH_SECRET`.

   For Google sign-in, create a separate Google client for local work. Set its
   authorized origin to `http://localhost:3000` and its only authorized redirect
   to `http://localhost:3000/api/auth/callback/google`. The redirect is where
   Google sends the browser after sign-in. Put this local client's ID and secret
   in `AUTH_GOOGLE_ID` and `AUTH_GOOGLE_SECRET`.

   Leave `ANTHROPIC_API_KEY` unset, including in your terminal environment. Keep
   `SCREENSHOT_EXTRACTOR=fake`. The fake extractor returns fixed rows for any
   uploaded screenshot and never calls Anthropic. Set it to `fake-failure` to see
   the "Couldn't read that screenshot" message. Without this setting, the app
   calls Anthropic when a key is set and shows that message when no key is set.
   Never set `SCREENSHOT_EXTRACTOR` on the real site. Admins can also use Sample
   analytics snapshots for their student side. An Admin reviews and approves
   each Sample analytics snapshot like an uploaded snapshot.

4. Start the app from the repository folder:

   ```bash
   npm run dev:local
   ```

   This command applies the database migrations with the values in `.env.local`,
   then starts the app on `localhost` with the fake screenshot reader. Google
   sign-in works only at `http://localhost:3000`, not at `127.0.0.1`. Use
   `npm run dev` when you set `SCREENSHOT_EXTRACTOR` yourself.

   Open `http://localhost:3000`. The local database starts empty. Sign up with
   Google to create your Account. This needs a local Google client in `.env.local`.
   Without one, use the verify helper's minted session cookies
   (`.agents/skills/verify/SKILL.md`). Do not copy real students' records into it.

5. Sign in once with Google locally. Then, in
   another terminal, make that local Account an Admin. `make-admin` refuses an
   Account that has not signed in with Google, and it clears any password. It reads
   `DATABASE_URL` from the terminal environment, so pass the local value explicitly:

   ```bash
   DATABASE_URL=postgresql://postgres:local-only@127.0.0.1:5432/drillmap npm run make-admin -- your-local-email@example.test
   ```

   Replace `your-local-email@example.test` with the email of the Google
   Account you used locally. Sign out and back in to see the Admin controls.

## Commands

```bash
npm run dev     # start the development server at http://localhost:3000
npm run dev:local  # apply migrations, then start at http://localhost:3000 with the fake screenshot reader
npm test        # run the scheduling-engine test suite
npm run lint    # run ESLint
npm run build   # create a production build
npm run start   # run a production build
```

Delete every student from the local database:

```bash
npm run reset:dev-data -- --yes
```

The reset removes all students and their Analytics snapshots, Weekly schedules,
and Activity check-ins in one transaction. Accounts and leads stay, so each
person signs in and goes through onboarding again. Without `--yes`, it stops
and names what it would delete. It refuses `NODE_ENV=production` before connecting.

The reset, `make-admin`, and `db:migrate` commands read
`postgres://` and `postgresql://` strings only. They allow database hosts
`localhost`, `127.0.0.1`, and `::1`. They check every host in the address and
in the `host` and `hostaddr` query settings, even when the address has no host.
They refuse remote hosts, other protocols, and missing or unreadable connection
strings before connecting. No flag or environment setting bypasses this check.

The guard also allows exact copy-site hosts committed in
[scripts/copyDatabaseHosts.json](scripts/copyDatabaseHosts.json).
That list is empty until the owner verifies the copy's hosts. Add only full,
lowercase host names for the copy, with no ports or credentials. Never add the
real site's host, a wildcard, or a provider-wide suffix.

The guard refuses Postgres service settings because they can load connection
settings from a separate file. See the [Postgres connection documentation](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-SERVICE).

The [v2 schedule specification](docs/specs/adaptive-weekly-schedules.md) records
the current rules.
