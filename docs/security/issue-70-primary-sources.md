# Issue 70 primary sources and dependency evidence

Research date: October 1, 2026. This note supports the local security audit. It records source mappings and dependency evidence, not an ASVS certification or proof of production exploitability. No dependency installation, application change, environment-value inspection, or production request was performed.

## Framework and identity evidence

The [bcrypt.js maintainer documentation](https://github.com/dcodeIO/bcrypt.js#security-considerations) states that input is limited to 72 UTF-8 bytes and the library does not implicitly reject longer values. The application passes unbounded password strings to bcrypt. This is relevant to ASVS 6.2.8; a character-count limit alone would not address multibyte input. A strict arbitrary-length password policy needs a suitable password hashing design rather than silent truncation.

The installed Next.js 16.3.1 guides at `node_modules/next/dist/docs/01-app/02-guides/authentication.md` and `data-security.md` say protected Server Actions must authenticate and authorize their direct POST calls. They describe Proxy as an optimistic check and recommend checks near the data. Server Actions compare Origin with Host or X-Forwarded-Host, but that behavior must not be assumed for ordinary Route Handlers. These are also documented in the [Next.js data-security guide](https://nextjs.org/docs/app/guides/data-security).

Google says `sub` is stable and never reused, while `email` may change and must not be the primary account identifier. The application queries only normalized email in its Google sign-in/JWT callbacks and does not inspect `profile.email_verified`. This supports an identity-association risk. It does not prove that an attacker can obtain a valid Google assertion for another user's email. See [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect#an-id-tokens-payload) and [Auth.js Google provider guidance](https://authjs.dev/reference/core/providers/google).

Installed Auth.js source supplies additional local evidence: `@auth/core/lib/utils/cookie.js` defaults to HttpOnly and SameSite=Lax; secure cookies and the __Secure- prefix depend on HTTPS URL handling. `@auth/core/lib/init.js` defaults session maxAge to 30 days. `@auth/core/jwt.js` encrypts session tokens and validates them through JOSE. The application does not configure an explicit maximum lifetime, revocation list, or per-user session version. Cookie and TLS behavior in production remains unverified.

ASVS 4.1.1 L1 requires response Content-Type to match the body; request Content-Type gating for cookie-authenticated JSON handlers belongs to 3.5.2 when used to guarantee a CORS preflight. See [API and web services](https://github.com/OWASP/ASVS/blob/v5.0.0_release/5.0/en/0x13-V4-API-and-Web-Service.md). Deletion step-up is 7.5.3 L3. Requirement 7.5.1 L2 covers authentication-sensitive account attribute changes and should not be presented as the exact deletion requirement. Backup access and retention evidence can support 14.1.2 and 14.2.4; this version has no standalone requirement explicitly naming backups.

## Dependency audit

Read-only commands `npm audit --json --ignore-scripts` and `npm audit --omit=dev --json --ignore-scripts` both completed with exit code 1 because advisories were found. The full result counted six vulnerable package entries: one critical, three high, and two moderate. The production-filtered result counted two entries: one critical and one high. These counts aggregate package entries, not independent exploitation paths. The lockfile was read to confirm the versions and dev flags. `npm explain` confirmed that sharp is an optional Next.js dependency, while the brace-expansion and js-yaml paths belong to lint tooling.

The registry suggested Next.js 16.3.8. That suggestion is recorded as audit output, not an applied upgrade. Vitest's audit fix suggestion was a major downgrade to 2.0.5, which does not substitute for reviewing the maintainer's fixed-version guidance. A later remediation should update the compatible framework/tooling set, verify resolved sharp, run regression checks, and repeat audit. No packages or lockfiles changed during this research.

Each of the three Next.js advisories above individually has Critical severity in the GitHub advisory API and its maintainer page. That label is not merely the aggregate package severity. All linked ASVS chapter and CSV paths were checked against the pinned release and returned HTTP 200.

Advisory data is a snapshot. `npm audit` does not test application reachability, unknown vulnerabilities, deployment settings, runtime OS, or whether development dependencies are present in the deployed artifact. No claim of confirmed RCE is made by this note.
