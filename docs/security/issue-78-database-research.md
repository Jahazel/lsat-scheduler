# Database choice: keep Atlas or move to hosted Postgres

Research for [issue 78](https://github.com/Jahazel/lsat-scheduler/issues/78), under [issue 69](https://github.com/Jahazel/lsat-scheduler/issues/69). Checked October 6, 2026, America/Chicago, against checkout `e01e0ec`. No provider settings, data, or code were changed. No database was opened. Sources are official provider pages. They state published terms, not measured restore times for DrillMap.

**Decision:** On October 6, 2026, the owner chose Postgres on Neon. See [Decision](#decision). The Atlas sections below record what was compared.

## Words in this file

- **Snapshot** means a full copy of the database at one moment.
- **Point-in-time restore** (PITR) means a restore to any moment inside a window, not only to a snapshot time.
- **Data loss target** (RPO) is the most data the site may lose: 1 day ([Recovery](release-gate.md#recovery)).
- **Recovery time target** (RTO) is the longest time to recover: 2 days.
- **Copy of the site** (staging) is the second deployment with its own database ([release gate](release-gate.md)).
- **Deletion list** holds deleted Account IDs for 30 days and runs again after every restore ([rules 30 to 32](issue-76-decisions.md#restores)).

## What DrillMap stores today

- Six collections: [User](../../src/models/User.ts), [Student](../../src/models/Student.ts), [Lead](../../src/models/Lead.ts), [WeeklySchedule](../../src/models/WeeklySchedule.ts), [AnalyticsSnapshot](../../src/models/AnalyticsSnapshot.ts), and [ActivityCheckIn](../../src/models/ActivityCheckIn.ts).
- A weekly schedule stores `schedule` and `generationInputs` as free-form nested documents. They cannot change after they are saved. An analytics snapshot stores `lrAccuracyByType` the same way.
- Mongo-specific features in use: one `populate` join in [students.ts](../../src/lib/students.ts), one transaction in [adminTestRepositories.ts](../../src/lib/adminTestRepositories.ts), `$in`/`$unset` operators, and unique indexes. No aggregation pipeline or `$lookup` exists.
- Sign-in uses JWT sessions with no database adapter ([auth.ts](../../src/auth.ts)). Only `UserModel` calls touch the database there.
- Production runs on the Atlas Free tier, MongoDB 8.0.32, AWS us-east-1, with backups inactive (issue 71). The data size was not read.

## Atlas Flex findings

These findings apply to Atlas Flex, which was not chosen. They are kept as the record of the comparison.

1. **Flex price and retention are correct.** $8 to $30 a month, one snapshot a day, the last 8 kept. Retention is fixed, so F4 ("no backup kept longer than 30 days") holds without a setting.
2. **The Flex restore target is unclear.** The restore page says Atlas "can't restore snapshots from Flex clusters, dedicated clusters, or Cloud Manager to a Flex cluster" ([restore page](https://www.mongodb.com/docs/atlas/backup/cloud-backup/restore-from-snapshot/)). The backup overview says Flex snapshots restore "to Flex cluster or M10 and greater tiers" ([backup overview](https://www.mongodb.com/docs/atlas/backup-restore-cluster/)). The API says "another flex cluster or dedicated cluster tier." **Unverified** until the first restore test. If a Flex target fails, use a temporary M10, or download the snapshot and copy it with `mongodump`/`mongorestore`.
3. **The copy of the site cannot use a Free database for check I2.** A Free cluster is not a restore target. The copy needs Flex ($8 a month more), or the restore test needs a temporary target.
4. **Flex cannot send a "backup failed" alert.** Flex alerts only cover Connections, Logical Size, Network, and Opscounter ([Flex limits](https://www.mongodb.com/docs/atlas/reference/flex-limitations/)). The backup alerts such as "Last snapshot too old" ([alert conditions](https://www.mongodb.com/docs/atlas/reference/alert-conditions/)) are not in that list. The required "Backup failed" alert ([Owner and alerts](release-gate.md#owner-and-alerts)) needs a job that reads the snapshot list through the Atlas API ([snapshot list API](https://www.mongodb.com/docs/api/doc/atlas-admin-api-v2/operation/operation-listgroupflexclusterbackupsnapshots)). A Vercel Hobby cron job can run once a day, within the hour ([Vercel cron limits](https://vercel.com/docs/cron-jobs/usage-and-pricing)). That job needs an Atlas API key, which is one more credential to protect.
5. **The "Flex costs more than $30" review trigger cannot fire.** Flex stops at $30 and then limits speed. A better trigger: Flex reaches 500 operations per second or 5 GB.
6. **No snapshot exists in the first 24 hours after the change, and Flex has no on-demand snapshot.** Take one `mongodump` copy just before the change. Delete it within 30 days (F4).
7. **Flex support for transactions is not stated** in the Flex limits page. **Unverified.** The account deletion transaction from issue 76 must pass on the copy of the site.

## Cost of a move to Postgres

The work below is an estimate from the code, not a measured plan.

- **Code:** 32 source files import Mongoose or the models. 12 test files and 11 scripts in `scripts/` do too. Each repository, server action, and page query needs a new query layer, such as Drizzle or Prisma with a Postgres driver.
- **Schema:** six tables. `schedule`, `generationInputs`, and `lrAccuracyByType` become JSONB columns. Weekly schedule immutability moves from Mongoose hooks to a database rule, for example no UPDATE permission or a trigger. The `populate` becomes a join.
- **IDs:** records use 24-character ObjectIds. Keeping them as text avoids changes to links and sessions. New IDs need a new rule.
- **Data move:** none. On October 6, 2026, the owner confirmed that the real database holds only the two admin accounts. The move starts with an empty database and creates those two accounts again.
- **Sign-in:** no adapter change. Only the `User` queries in `auth.ts` change.
- **Release gate:** the database user, network, and alert rules in [issue 77](issue-77-decisions.md) must be decided again for the new provider (rule 3). Rule 5 uses Atlas temporary database users, which expire on their own; Neon has no such feature in the sources checked.

## Decision

On October 6, 2026, the owner chose to move DrillMap from MongoDB Atlas to Postgres on Neon, before launch.

**Why Postgres.** DrillMap's records are linked: an activity check-in belongs to a weekly schedule, a weekly schedule and an analytics snapshot belong to a student, and a student belongs to an Account. Postgres enforces these links in the database. MongoDB leaves them to the app code.

- Account deletion is now six separate steps in [deleteStudentAccount.ts](../../src/lib/deleteStudentAccount.ts). A failure partway leaves orphan records. Postgres foreign keys can delete linked records together, all or nothing.
- A weekly schedule must not change after it is saved. Today only Mongoose hooks stop a change ([WeeklySchedule.ts](../../src/models/WeeklySchedule.ts)). Postgres can refuse the change in the database.
- The nested parts of a weekly schedule and an analytics snapshot fit JSONB columns.
- Many hosts run standard Postgres. `pg_dump` moves the data to another host.
- The real database holds only two admin accounts, so this is the cheapest time to move.

**Why Neon.** It is the cheapest host checked with real backups, about $5 a month with the copy of the site. It is the only cheap host with PITR, so data loss stays well under 1 day. A restore goes to a new branch, which meets I2. It supports passkey sign-in and a limited role made in SQL. See [Postgres hosts](#postgres-hosts).

**Rules for the move.** These come from the findings above:

1. The real site uses the Neon Launch plan. Set a history window of at least 1 day, a daily snapshot schedule, and snapshot retention of 30 days or less (I1, F4).
2. The copy of the site uses a separate Neon project, not a branch. A branch reuses the parent's role passwords.
3. The app connects with a role made in SQL that can only read and write DrillMap's tables. It is not a `neon_superuser`.
4. A daily job checks the age of the newest snapshot and alerts the owner. Neon documents no backup-failure alert.
5. Delete restore branches and `_old_` branches after use (F4).
6. The privacy page names the new provider and backup period in the same change (release-gate workflow step 2).
7. After the two admin accounts work on Neon, delete the Atlas project.

## Findings added during the final assessment

Checked October 6, 2026, while preparing [the public-signup assessment](issue-69-assessment.md). These facts refine the implementation plan. The owner decisions are recorded separately in the assessment; these findings alone do not approve access exceptions.

- **Snapshot retention has an exception.** Neon keeps the latest scheduled snapshot while its schedule remains active, even after its retention deadline. Manual snapshots also need an explicit expiration or deletion. Setting retention to 30 days does not by itself prove the launch check that no backup is older than 30 days. The backup checker must inspect actual ages and the recovery procedure must remove expired copies, including the retained latest snapshot when necessary. The removal procedure must account for Neon's latest-snapshot protection. See [snapshot retention](https://neon.com/docs/guides/backup-restore#snapshot-retention).
- **Project-only API keys have write powers.** An organization key scoped to one project has Editor access and can change or delete project resources. It is not a read-only snapshot key. API keys remain valid until revoked. A separate Collaborator account with Viewer access only to production can provide a read-only personal API key under Neon's new permissions model. Existing organizations and Vercel-managed organizations may still use legacy permissions. Verify the available model before provisioning the checker. See [API keys](https://neon.com/docs/manage/api-keys), [permissions](https://neon.com/docs/manage/user-permissions), and [snapshot list API](https://neon.com/docs/reference/api/snapshots/list-snapshots).
- **Owner-access expiry needs explicit cleanup.** PostgreSQL's `VALID UNTIL` expires password authentication, not the role or its privileges, and does not end already open sessions. A temporary-access plan must also disable the login, terminate its sessions, remove its privileges, and delete the role when the job ends. See [Neon roles](https://neon.com/docs/manage/roles) and [PostgreSQL CREATE ROLE](https://www.postgresql.org/docs/current/sql-createrole.html).
- **The app role needs explicit SQL grants.** Roles created through the Neon Console, CLI, or API receive `neon_superuser` membership. A role created through SQL does not automatically receive that membership. Grant only the app's required database, schema, table, and sequence permissions. Generic read/write examples can include schema creation, which the running app does not require. See [Neon roles](https://neon.com/docs/manage/roles) and [database access](https://neon.com/docs/manage/database-access).
- **Launch uses the public endpoint.** Neon's IP Allow needs Scale. Neon refuses unencrypted connections and recommends `sslmode=verify-full` to check the server certificate. The driver choice must preserve those checks. See [IP Allow](https://neon.com/docs/introduction/ip-allow) and [secure connections](https://neon.com/docs/connect/connect-securely).
